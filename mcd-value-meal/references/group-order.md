# 模块：多人分餐与方案校验

## 1. 输入解析

用户说：「6 个人，总预算 150 元，2 个人不吃辣。」

要拆成：

| 要素 | 值 |
|---|---|
| 总预算 | 150 元（**不是人均**） |
| 人均上限 | 150 ÷ 6 = 25 元 |
| 用餐人 | D1…D6，编号唯一 |
| 忌口 | D1、D2 `spicyAllowed=false`，其余不加限制 |

**总预算误当人均预算是本模块最常见的错误**：6 人 25 元/人 ≠ 6 人各 150 元。

只补问缺失项：**位置或门店、就餐方式、用餐时间、每人最低需求**。其余不要重复问。

## 2. 每人最低需求

用结构化字段表达，不要用自然语言含糊描述：

```json
{ "dinerId": "D1", "spicyAllowed": false, "minReq": { "main": 1 } }
```

- `minReq` 是角色 → 份数：`main` 主食、`side` 小食、`drink` 饮品、`dessert` 甜品。
- 用户没说就默认 `{"main": 1}`，并在输出里说明这个默认。
- 用户说"每人要一个汉堡加一杯饮料" → `{"main": 1, "drink": 1}`。

## 3. 校验顺序（不可颠倒）

```
1. 结构校验     编号唯一 / 每人有餐 / 满足 minReq
2. 忌口校验     不吃辣 → 辣味淘汰，辣度未知也淘汰
3. 数量校验     分配份数 ≤ 采购份数；请求份数 vs 接口 actualQty
4. 券校验       一套方案 ≤ 1 张券；同一券实例不得跨订单复用
5. 费用校验     现金整数分；逐项相加与接口总额对齐；积分独立
6. 预算过滤     cashCent ≤ 预算
7. 排序         cashCent 升序 → pointsCost 升序
```

先校验需求，再做预算和排序。反过来会把"便宜但不满足需求"的方案排到第一。

## 4. 忌口细则

| 情况 | 判定 |
|---|---|
| 餐品 `spicy` | 不吃辣者分配 → **违规** |
| 餐品 `not-spicy` | 允许 |
| 餐品 `unknown`（接口未返回辣度） | 不吃辣者分配 → **违规**（不能当作通过） |
| 无辣度限制的人被分到辣餐 | 允许，但**不得因为"他能吃辣"就优先给他分辣餐** |

`query-meals` **不返回辣度字段**。所以辣度只有三种可能来源：

1. 商品名明确含"辣"（如麦辣鸡腿堡、龙焰鸡腿堡）→ `spicy`，可靠。
2. `query-meal-detail` 的组成/描述里明确写不辣 → `not-spicy`。
3. 其余一律 `unknown`。

给不吃辣的人配餐时，必须走第 2 条去核验，否则方案一律不通过。这是设计上的强约束，不要绕过。

## 5. 套餐与特调

- 需要套餐组成（判断里面有没有辣、有没有饮品）时，必须调 `query-meal-detail`。
- 没调就把 `componentsVerified=false`，方案降级为**条件方案**，并在输出里写清"未核验套餐组成"。
- `query-meal-detail` 返回 `supportModify=true` 时才存在特调；特调 `key` 规则见 `tool-map.md`，本模块不展开。

## 6. 共享餐品

```json
"shared": [ { "lineId": "L7", "dinerIds": ["D1","D2","D3","D4","D5","D6"], "qty": 1 } ]
```

- 共享行只算**一次采购**，不按人头乘以份数。
- 逐人清单里只标「[共享]」，**不带份数**——否则 6 人共享 2 杯可乐会被读成"每人 2 杯"。
- 共享段单独列出：`可乐×2，6 人共享`。
- 共享小食可以计入 `side` 需求，但不能计入 `main` 需求。

## 7. 数量二次校验

`calculate-price` 会静默改数量（请求 2 份 + 1 张券 → 返回 1 份）。因此每行必须写 `actualQty`，脚本用它复核：

- `actualQty < qty` → `ACTUAL_QTY_SHORT`，方案淘汰或重新分配。
- 不提供 `actualQty` → `QTY_UNVERIFIED` 警告，不得宣称数量已核验。

## 8. 单订单与拆单

- **默认单订单**。
- 只有在两个条件同时成立时才比较拆单：① 规则允许（每单都能独立成单、券各自可用）；② 用户明确接受拆单。
- 拆单方案用 `orders[]` 表达，每单有自己的 `items` / `allocation` / `cashCent` / `pointsCost`。
- 合计口径：现金 = 各单之和；积分 = 各单之和；券使用次数 = 各单券实例计数。
- **同一张具体券实例（`couponCode`）不能出现在两个订单里**，脚本用 `COUPON_REUSED` 拦截。
- 拆单的代价要讲清楚：多笔配送费、多张券被占用、取餐要分两次。

## 9. 多人 ≠ 企业团餐

多人一起点单，`beType` 仍然是用户选择的就餐方式（通常 `1` 到店自取）。**不要因为人多就自动切到 `beType=6` 团餐**。只有用户明确说"企业团餐/公司订餐"才走团餐链路。

## 10. 输出六段

1. **逐人分配**：每人编号、忌口标记、餐品与数量、共享标记。
2. **共享餐品**：名称、总份数、几人共享。
3. **采购总清单**：每行商品、份数、接口实际份数、所用券。
4. **所用优惠券及可用份数**：券名、券码后 8 位、覆盖几份。
5. **现金总支出 / 积分总消耗 / 平均现金支出**：三者分列，积分不折算成钱。
6. **校验结果**：预算、人数、忌口、实际数量四项逐一写"通过/不通过 + 原因"。

页脚：查询时间、门店、就餐方式、预算口径（总额与人均）。

## 11. 用脚本跑

```bash
python scripts/plan_math.py rank --input examples/group-6p-150.mock.json
python scripts/plan_math.py validate --input examples/group-6p-150.mock.json --plan-id P3 --people 2
```
