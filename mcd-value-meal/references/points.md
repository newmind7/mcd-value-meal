# 模块：积分适配与兑换

## 1. 工具链与上游依赖

```
query-my-account                     → 可用积分 availablePoint / 临期积分 currentMouthExpirePoint
        │
mall-points-products(catRuleIds=1>4) → spuId 列表（商品券）
        │
mall-product-detail(spuId)           → skuId / points / price / upTime / downTime / shopId / note
        │
mall-create-order(skuId, spuCategory, count) → orderId / couponCodes / status
        │
mall-order-list / mall-order-detail   → 超时核查
```

关键：**兑换入参是 `skuId`，不是 `spuId`**。`spuId` 只能用来查详情。

## 2. 积分字段是字符串且可能是小数

实测 `availablePoint: "49.6"`。所以：

- 比较积分用量时用**十进制**处理，不要直接 `int()` 截断（49.6 → 49 会造成"够/不够"的误判）。
- 展示保留接口原值 `49.6`，不四舍五入成 `50`。
- 现金与积分**分开两列**，不做任何折算。

## 3. 三类方案对比

| 方案 | 定义 | 何时推荐 |
|---|---|---|
| **A. 不兑换** | 完全用现有券 + 现金，不动积分 | 基准方案，永远要给出来 |
| **B. 兑换降现金** | 用积分换券，让本次现金支出更低 | 兑换品确实能用在这家店这一单，且现金确实下降 |
| **C. 临期积分消化** | 优先用即将过期的积分换本次要吃的餐品 | `currentMouthExpirePoint > 0` 且兑换品匹配本次需求 |

**A 永远不能被省掉**。"不兑换也能吃"是用户判断值不值得兑换的前提。

## 4. 排序规则（固定）

```
1. 满足人数与忌口
2. 现金在预算内
3. 现金支出更低者优先
4. 现金相同时，积分消耗更少者优先
```

不得自定义权重、不得把积分按某个比例折成现金去比较。**没有官方折现比例，就不要造一个。**

## 5. 节省金额的显示条件

只有在**同等餐品、同店、同时间**且现金基准可验证时，才能说"用积分省了 X 元"。

```
省的钱 = 不兑换方案的现金（可验证） − 兑换方案的现金（可验证）
```

且必须同时说明付出了多少积分。任一条件不满足 → 只报"现金支出 X 元 + 积分 Y 分"，不说"省了多少"。

## 6. 兑换品过滤（先过滤，再展示）

逐个检查，任一不满足就排除：

| 检查 | 不满足时的处理 |
|---|---|
| `upTime` / `downTime` 是否覆盖本次就餐时间 | 排除，注明"不在可兑换窗口" |
| `status` 是否上架（2=上架；1 仓库 / 3 售罄 / 4 下架 / 5 预热） | 排除，注明状态 |
| `shopId` 是否匹配（`mall-create-order` 仅 `shopId=2`） | 排除，party 类 `shopId=5` 需走 `party-order-create`，本技能不接入 |
| 兑换品适用门店是否包含当前门店 | 排除，注明"不适用当前门店" |
| 兑换券能否用于当前渠道（到店/外送）与时段 | 排除 |
| 到账是否来得及（虚拟券是否即时到账） | 来不及就排除，不要赌 |
| 积分是否够（用十进制比较） | 不够就说明差多少 |

## 7. 未持有的兑换券不能当已持有

这是本模块最容易出错的地方：

- 用户还没兑换时，这张券**不在券包里**，`query-store-coupons` 也查不到。
- 因此**不能**把它直接塞进 `calculate-price` 的 `items[].couponCode` 去跑真实试算——那等于伪造券码。
- 正确做法：标为**条件方案**，写明"需先兑换 X（Y 积分）后，预计现金 Z 元；未经真实试算，条件未验证"。
- 只有兑换成功、券真正到账并出现在 `query-store-coupons` 里，才做真实试算。

## 8. 授权门槛

**扣积分前必须展示清单并取得针对该清单的明确授权**：

| 必须展示 | 说明 |
|---|---|
| 兑换商品名 | 完整名称 |
| `skuId` | 具体规格，不是 spuId |
| 数量 | 兑换几份 |
| 消耗积分 | 精确到小数 |
| 现金支出 | `price` / `extTradePrice` |
| 有效期 | `upTime` ~ `downTime` |
| 使用条件 | `note` 原文概述（门市/时段/人数限制） |

授权粒度：

- **单次授权**：只对这一次清单有效，下次重新确认。
- **范围授权**：用户明确说"预算 100 元内、兑换券类、别超过 200 积分就自己换"——才可在该范围内自动兑换，且必须在执行后完整复述换了什么。

## 9. 兑换后必须刷新

```
mall-create-order 成功
  → query-my-account       （积分余额、冻结积分）
  → query-my-coupons       （券是否到账）
  → query-store-coupons    （本店是否可用）
  → 重新 calculate-price   （金额重算）
```

不刷新就用旧数据算价，会出现"积分扣了、价格没变"的错账。

## 10. 超时与部分成功

| 情况 | 处理 |
|---|---|
| 兑换超时 / 结果未知 | **先 `mall-order-list` → `mall-order-detail` 查实际状态**，确认到底扣没扣。不重复下单 |
| 返回 `status=2`（部分成功） | 按 `orderItemStatus` 逐项判断，只处理未成功的部分 |
| 返回 `status=0`（失败） | 说明失败原因，积分未扣则可重试一次；已扣则先查订单 |
| 多商品兑换 | 一商品一订单，**串行排队**，前一笔成功后再下一笔；不要并发 |

## 11. 禁止

- 不假设积分折现比例。
- 不把积分算进"现金总支出"。
- 不为了"用掉临期积分"而买本次不需要的东西。
- 不在未授权时调用 `mall-create-order`。
- 不把 `spuId` 当 `skuId` 传。
